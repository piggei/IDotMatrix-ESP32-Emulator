# iDotMatrix ESP32 Emulator

Experimental ESP32 firmware that emulates iDotMatrix BLE displays and communicates directly with the official iDotMatrix app.

<p align="center">
  <img src="assets/idotmatrix-esp32-demo.jpg" alt="iDotMatrix ESP32 Emulator running on a 16x16 LED matrix" width="700">
</p>

The project was created by reverse engineering BLE traffic generated by the app, without owning an original device during the initial work. The goal is to reproduce the protocol on ESP32 hardware and document the observed behaviour.

> Current development status: **v0.3.1-dev / BUILD 89**. The public stable baseline remains **v0.3.0 / BUILD 80**. BUILD 89 migrates Alarm/Schedule GIF playback from the legacy full-RAM path to an isolated LittleFS-backed PLAY file. BUILD 88, including the multi-packet Bulk timeout hotfix, has been hardware-tested successfully. The 16x16 profile remains the default stable hardware target; 32x32 and 64x64 app profiles have also been successfully emulated and tested at protocol/media level.

## Release and build identifiers

The project deliberately uses two different identifiers:

- **release**: the public project version, for example `v0.3.0`;
- **build**: the internal incremental firmware development number, for example `BUILD 80`.

Current mapping:

- `v0.3.0` = `BUILD 80` (stable baseline);
- `v0.3.1-dev` = `BUILD 89` (current consolidation build; Alarm/Schedule GIF LittleFS playback migration).
- `v0.3.1-dev / BUILD 88` = multi-packet Bulk timeout/mutex hotfix; hardware-tested successfully.
- `v0.3.1-dev / BUILD 87` = OTA/LittleFS safety hardening milestone; hardware testing exposed the multi-packet timeout regression fixed in BUILD 88.
- `v0.3.1-dev / BUILD 86` = cross-core synchronization/callback-latency milestone; hardware-tested successfully.
- `v0.3.1-dev / BUILD 85` = runtime-correctness hardening milestone; hardware-tested successfully.
- `v0.3.1-dev / BUILD 84` = Arduino preprocessing/forward-declaration hotfix for BUILD 83.
- `v0.3.1-dev / BUILD 83` = transactional Alarm/Schedule/GIF hardening milestone.
- `v0.3.1-dev / BUILD 82` = parser/transfer hardening milestone.
- `v0.3.1-dev / BUILD 81` = documentation/hygiene-only consolidation milestone.

A development build must not be described as a verified public release until its changes have been tested on hardware.

## Parser and transfer hardening

BUILD 82 adds defensive checks without redefining the observed iDotMatrix protocol:

- date/time synchronization is accepted only when month/day/time fields form a valid calendar value; malformed values are ignored while the existing compatibility ACK is preserved because negative ACK semantics are not yet known;
- incomplete logical-packet reassembly is discarded after 5 seconds of inactivity;
- an incomplete Bulk transaction is aborted after 30 seconds without Bulk activity;
- abandoned GIF RX temporary files are removed when a transfer is aborted, times out, overflows, or the BLE link disconnects;
- TEXT Bulk payloads declaring more than `MAX_TEXT_PAYLOAD` (4096 bytes) are rejected instead of being silently truncated and parsed.

The 5 s / 30 s timeout values are emulator safety limits, not timings inferred from original iDotMatrix hardware.

## Transactional media/state hardening

BUILD 83 reduces the risk of filesystem metadata and runtime state diverging during media replacement:

- Alarm commands are staged in a temporary record and the in-memory slot is published only after validation, media replacement and NVS persistence succeed; existing media is kept as a backup until the new slot is committed;
- Schedule uploads keep their global flags, metadata and media in staging until the inactivity commit point. Existing Schedule files are first moved to backups, all received media are preflighted by size/CRC, and failures trigger rollback instead of publishing a partial Schedule;
- on boot, Alarm/Schedule backup files are reconciled against the persisted metadata size/CRC, allowing an interrupted replacement to select the file that matches the committed metadata;
- normal GIF RX -> PLAY replacement now preserves the previous PLAY file until the new RX file has been promoted successfully. A leftover PLAY backup is recovered after reboot if no PLAY file exists;
- Alarm explicitly preempts an active Schedule before loading Alarm media, avoiding the previous ordering where Schedule teardown could stop the newly started Alarm GIF;
- Alarm/Schedule clock fields are sanity-checked before their staged configuration is accepted.

These mechanisms are best-effort transaction/rollback guards on LittleFS + Preferences; they are not presented as a filesystem-wide ACID transaction or as behavior observed on original iDotMatrix hardware.


## Runtime correctness hardening

BUILD 85 tightens emulator runtime behavior without claiming new original-device protocol semantics:

- ECO/power-saving brightness is re-evaluated once per second, so a static framebuffer now changes brightness when the configured interval begins or ends even when no renderer requests a refresh;
- malformed power-saving records (invalid hour/minute/reduction fields) are ignored while the existing compatibility ACK is preserved because an original-device error ACK is still unknown;
- runtime soft reset now clears all transient display state, active Alarm/Schedule markers and deferred GIF-open state so content cannot reappear from stale runtime flags after the reset; persistent Alarm/Schedule definitions, clock synchronization, brightness, ECO configuration and screen power are intentionally retained;
- when RTC support is compiled in, `rtc.lostPower()` now marks the RTC time as invalid. Alarm, Schedule and ECO do not use that RTC value until a valid BLE time synchronization updates it.

The soft-reset and ECO policies above are emulator implementation behavior. Exact original-device behavior remains only partially reverse-engineered.

## Cross-core synchronization hardening

BUILD 86 serializes shared protocol/runtime state between FA02/server BLE callbacks and the Arduino `loop()` with a FreeRTOS task mutex. Earlier builds deliberately deferred AnimatedGIF open/teardown work to `loop()`, but scalar flags, packet/Bulk timeout cleanup, renderer state and connection state could still be read or modified concurrently on the ESP32 BLE task and loop task. BUILD 86 removes the remaining reliance on `volatile` as a synchronization mechanism for those paths.

The mutex is intentionally a scheduler mutex rather than a critical-section spinlock: filesystem, decoder and rendering operations may block and therefore must not execute with interrupts disabled. This does **not** yet move the complete FA02 parser/filesystem pipeline out of the BLE callback; that larger architectural change remains tracked as technical debt.

BUILD 88 fixes one concurrency/timing regression exposed by hardware testing of BUILD 87. After BUILD 86 introduced the runtime mutex, `loop()` still captured its `millis()` snapshot before waiting for that mutex. A BLE callback could therefore update the protected packet/Bulk receive timestamp while the loop was blocked, making the loop snapshot older than the new receive timestamp. The unsigned timeout subtraction then wrapped and could immediately abort an otherwise healthy multi-packet transfer. BUILD 88 takes the time snapshot only after acquiring the mutex. Timeout durations and protocol semantics are unchanged.

BUILD 87 hardens optional infrastructure without changing observed BLE command semantics:

- ArduinoOTA remains disabled by default, and enabling it with the repository Wi-Fi placeholders or the development OTA password now fails at compile time;
- the OTA password must be at least eight characters;
- LittleFS is mounted without automatic formatting. A normal mount failure therefore does not silently erase Alarm/Schedule/GIF media;
- intentional format-on-mount-failure recovery is available only through `LITTLEFS_FORMAT_ON_MOUNT_FAIL=1`, which is disabled by default;
- when LittleFS is unavailable, persistent Preferences metadata is still loaded, but filesystem-backed media operations fail safely instead of pretending storage is available;
- normal Bulk GIF reception checks current LittleFS free space before opening an RX file.

BUILD 89 removes the legacy full-RAM GIF path used by Alarm/Schedule. Their persistent transactional media files are never opened directly by AnimatedGIF: before playback, the selected GIF is copied and CRC-checked into the disposable `/event_play.gif` file. The decoder opens only this isolated PLAY copy, so later staging/backup/rename operations on Alarm/Schedule source files cannot invalidate an active decoder file handle. The event PLAY file is removed when playback stops and is discarded at boot because it is never authoritative persistent state.

The disconnect callback no longer calls `delay(300)`. It records a deferred advertising-restart request, and `loop()` restarts advertising after the same 300 ms interval. This preserves the established reconnect timing while removing an avoidable sleep from the BLE callback.

## Hardware used

- DollaTek ESP32 OLED 0.96" development board (classic ESP32 + CP2102)
- 16x16 WS2812B matrix (256 LEDs), data on **GPIO 17**
- onboard 128x64 SSD1306 OLED via U8g2 software I2C
- active buzzer on **GPIO 18**, implemented with a non-blocking trill pattern
- RTC: planned optional extension; RTC modules have not yet been integrated

## Current capabilities

- BLE advertising and iDotMatrix app discovery
- device profiles `0x01` 16x16, `0x03` 32x32 and `0x04` 64x64
- time/date sync, brightness and screen control
- clocks with app-selected visual effects and optional date cycle (30 s HH:MM / 5 s DD/MM)
- matching vertical stopwatch/countdown UI with animated timer hand
- stopwatch remains white; countdown changes to red for the final five seconds
- scoreboard, effects, graffiti/drawing and text
- 8x16 (`0x02`) and 16x32 (`0x05`) text glyph records
- SimSun/SimHei observed as app-side rasterization: the ESP32 receives glyph bitmaps
- GIF/cloud animation reception and playback
- 4096-byte bulk chunks with CRC validation
- LittleFS-backed GIF reception for large 32x32/64x64 assets
- isolated RX/PLAY files and a fresh AnimatedGIF decoder for every media switch
- Alarm and Schedule support, including active buzzer output
- Alarm/Schedule GIF playback through an isolated LittleFS event PLAY file
- event-driven OLED diagnostics and unknown-command reporting

## Resolution profiles

Normal operation is native 1:1 and defaults to 16x16:

```cpp
#define IDOTMATRIX_SCREEN_TYPE 1
#define ENABLE_LOGICAL_TO_PHYSICAL_PREVIEW 0
```

Supported screen types currently known by this firmware:

| Type | Logical resolution | Status |
|---|---:|---|
| `0x01` | 16x16 | stable physical target |
| `0x03` | 32x32 | app/profile behaviour verified |
| `0x04` | 64x64 | app, cloud GIF transfer and playback verified |

During reverse-engineering, larger logical profiles were displayed on the physical 16x16 panel using a diagnostic nearest-neighbour preview. That scaling path is now **disabled by default**. To intentionally repeat those tests:

```cpp
#define IDOTMATRIX_SCREEN_TYPE 4
#define ENABLE_LOGICAL_TO_PHYSICAL_PREVIEW 1
```

Do not enable preview for normal/native hardware operation.

## 64x64 findings

The official app accepts screen type `0x04` and serves 64x64-specific cloud animations. Tests successfully received and played GIFs approaching 80 KB on the classic ESP32. The important architectural change was not more RAM: large GIFs are streamed to LittleFS, RX and PLAY files are isolated, and the AnimatedGIF decoder is destroyed/recreated for each media change. This removed the heap corruption and BLE disconnects seen during early 64x64 experiments.

## Buzzer

The tested Arduino-kit buzzer is an **active buzzer**. GPIO18 is therefore driven digitally rather than with `tone()`. Alarm/Schedule audio uses a non-blocking three-pulse trill so BLE, LEDs and OLED continue running.

## Related projects and acknowledgements

This project focuses on the opposite BLE role from most public iDotMatrix projects: the ESP32 acts as a **peripheral/server emulator** so that the official iDotMatrix app connects to it directly. The following projects have been especially useful for comparison, independent validation, and original-hardware research:

- [`dallanwagz/idotmatrix-ha`](https://github.com/dallanwagz/idotmatrix-ha) — Home Assistant integration and detailed protocol research validated against original iDotMatrix hardware, including larger display models.
- [`markusressel/idotmatrix-api-client`](https://github.com/markusressel/idotmatrix-api-client) — actively maintained Python API client for controlling iDotMatrix displays.
- [`derkalle4/python3-idotmatrix-client`](https://github.com/derkalle4/python3-idotmatrix-client) — important early public Python client and reverse-engineering reference.
- [`8none1/idotmatrix`](https://github.com/8none1/idotmatrix) — protocol research including APK/Bluetooth capture analysis and useful transfer observations.
- [`nj-designs/go-idot`](https://github.com/nj-designs/go-idot) — Go implementation of an iDotMatrix client.
- [`whybutter/idotmatrix`](https://github.com/whybutter/idotmatrix) — ESP32/Home Assistant-oriented controller for original iDotMatrix hardware; especially complementary to this project because it exercises the opposite BLE role and provides access to real-device testing.

These projects are complementary rather than competing implementations. Findings are cross-checked where possible, while this repository keeps emulator-derived observations clearly distinguished from behavior verified on original hardware. See [`docs/PROTOCOL-COMPARISON.md`](docs/PROTOCOL-COMPARISON.md).

## Security considerations

The default firmware is an experimental BLE peripheral emulator and does not currently require BLE pairing/authentication before accepting iDotMatrix commands. A nearby BLE central able to connect to the advertised device can therefore control the display and send supported configuration/media commands. This behavior is kept for compatibility with the official app and should not be interpreted as an authenticated control channel.

Wi-Fi/ArduinoOTA support is compile-time optional and disabled by default. BUILD 87 adds compile-time guards: a build with `OTA_ENABLED=1` fails if the repository Wi-Fi placeholders are still present, if the development OTA password `idotmatrix-ota` is still present, if any credential string is empty, or if the OTA password is shorter than eight characters. These checks prevent accidental deployment of the repository defaults; they do not turn OTA into a substitute for network isolation or BLE authentication.

## LittleFS safety and recovery

BUILD 87 no longer calls `LittleFS.begin(true)`. The normal boot path uses a non-formatting mount, so a partition/mount error does not automatically destroy persisted media. If a new or intentionally reset device truly requires formatting, set `LITTLEFS_FORMAT_ON_MOUNT_FAIL` to `1`, flash once to perform the explicit recovery path, verify the filesystem mounts, and return the option to `0` for normal use.

When LittleFS is offline, the emulator can still load Preferences metadata and continue with non-filesystem features, but filesystem-backed GIF, Alarm media and Schedule media cannot be stored or played until storage is available.
