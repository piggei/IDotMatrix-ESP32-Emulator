# iDotMatrix ESP32 Emulator

Current development build: **v0.5.0-dev / BUILD 141**. BUILD 141 is the consolidation baseline after hardware validation of the official app's **Preset / Default** section. Mixed GIF/image and TEXT media addressed to volatile device slots `14..19` are staged separately from the persistent Carousel bank, and `06/02 <count> <slots...>` activates up to six items in the supplied order. Images/GIFs use the observed ~3-second dwell; Preset TEXT timing follows the text presentation mode (scroll until the final glyph exits, or all required pages plus an approximately 3-second final hold). Captured Preset objects consistently carry `timeSign=5`; that field is retained as opaque metadata rather than interpreted as seconds.

> Development branch: **v0.5.0-dev / BUILD 141** uses the WLED-family `ESP32-HUB75-MatrixPanel-I2S-DMA` output path on MatrixPortal S3, preserves the hardware-validated MTU, Alarm and Program/Schedule fixes, and includes the hardware-validated volatile Preset/Default playback bank. PlatformIO remains the recommended development path and Arduino IDE compatibility is retained where practical.


Experimental ESP32 firmware that emulates iDotMatrix BLE displays and communicates directly with the official iDotMatrix app.

The project was created by reverse engineering BLE traffic generated by the app, without owning an original device during the initial work. The goal is to reproduce the protocol on ESP32 hardware and document the observed behaviour.

> Current stable release: **v0.4.0 / BUILD 118**. BUILD 118 is the final packaging release based on the hardware-tested BUILD 117 release candidate. No runtime feature changes were introduced after BUILD 117; the final pass updates release identifiers, hardware-support status and release documentation.


## Original 64×64 hardware findings and emulator policy

A physical iDotMatrix 64×64 unit is now used as a hardware oracle. The observations below are direct hardware findings; selected emulator UX differences are deliberate.

Observed on the original hardware:

- the Device Assets carousel is persistent and automatically resumes after a power cycle;
- Preset/Default accepts up to six mixed TEXT/GIF-image items in slots `14..19`; the app re-sends the selected media when invoked. Images/GIFs advance after roughly three seconds, while TEXT advances according to its presentation mode: scrolling text completes when the last glyph leaves the display, and page/static modes show all required pages then hold the last view for roughly three seconds;
- the unit has no persistent RTC: after a power cycle Alarm/Program execution requires a new app time synchronization, while the software clock continues to run after BLE disconnect as long as power is maintained;
- Alarm uses repeating three-beep trills;
- Program/Schedule uses the same repeating trill for roughly 30 seconds on the original device;
- Countdown completion is silent on the original device;
- Power Saving reduces matrix brightness as expected;
- Flip rotates the complete display by 180 degrees;
- leaving Cloud GIF or Graffiti in the app returns the original device to its background content instead of keeping the transient content visible;
- device reset removes the stored Device Assets content and also clears the password remembered by the original device/app workflow;
- Original 64×64 advertising has been correlated with MCU version `5.11` (`screenType=4`, version bytes `5,11`). BUILD 109 encodes the emulator release major/minor directly in the 9-byte Device Info FA03 response; `0.4.0-dev` is exposed through the Device Info response as bytes `00 04`, which the official app was hardware-tested to display as MCU `0.04`. BUILD 108 showed that manufacturer-data changes alone do not alter the MCU value displayed by the app. The internal BUILD number remains separate and is not encoded in this two-byte app-facing field.

Intentional emulator policy:

- no boot logo, boot fade or BLE-connect animation; a single low-priority 90 ms buzzer pulse provides connection feedback instead;
- Cloud GIF and Graffiti remain visible after leaving their app section;
- Alarm keeps the repeating three-beep pattern;
- Program/Schedule now emits one three-beep trill only;
- Countdown completion emits one three-beep trill (an emulator convenience; the original is silent);
- boot priority is **valid optional RTC → Clock**, otherwise **valid stored Carousel → Carousel**, otherwise **screen off**;
- reset clears Carousel, the volatile Preset/Default bank, Alarm, Schedule, brightness, ECO and rotation. It is deliberately a live device-state reset rather than a simulated power cycle: BLE remains connected, the volatile synchronized clock is preserved, and the matrix stays logically ON with a black framebuffer. Password support is currently documented but not implemented.

## Parser and transfer hardening

BUILD 82 adds defensive checks without redefining the observed iDotMatrix protocol:

- date/time synchronization is accepted only when month/day/time fields form a valid calendar value; malformed values are ignored while the existing compatibility ACK is preserved because negative ACK semantics are not yet known;
- incomplete logical-packet reassembly is discarded after 5 seconds of inactivity;
- an incomplete Bulk transaction is aborted after 30 seconds without Bulk activity;
- abandoned GIF RX temporary files are removed when a transfer is aborted, times out, overflows, or the BLE link disconnects;
- TEXT Bulk payloads declaring more than `MAX_TEXT_PAYLOAD` (4096 bytes) are rejected instead of being silently truncated and parsed.

The 5 s / 30 s timeout values are emulator safety limits, not timings inferred from original iDotMatrix hardware.

## Transactional media/state hardening

BUILD 83 reduces the risk of filesystem metadata and runtime state diverging during media replacement:

- Alarm commands are staged in a temporary record and the in-memory slot is published only after validation, media replacement and NVS persistence succeed; existing media is kept as a backup until the new slot is committed;
- Schedule uploads keep their global flags, metadata and media in staging until the inactivity commit point. Existing Schedule files are first moved to backups, all received media are preflighted by size/CRC, and failures trigger rollback instead of publishing a partial Schedule;
- on boot, Alarm/Schedule backup files are reconciled against the persisted metadata size/CRC, allowing an interrupted replacement to select the file that matches the committed metadata;
- normal GIF RX -> PLAY replacement now preserves the previous PLAY file until the new RX file has been promoted successfully. A leftover PLAY backup is recovered after reboot if no PLAY file exists;
- Alarm explicitly preempts an active Schedule before loading Alarm media, avoiding the previous ordering where Schedule teardown could stop the newly started Alarm GIF;
- Alarm/Schedule clock fields are sanity-checked before their staged configuration is accepted.

These mechanisms are best-effort transaction/rollback guards on LittleFS + Preferences; they are not presented as a filesystem-wide ACID transaction or as behavior observed on original iDotMatrix hardware.


## Runtime correctness hardening

BUILD 85 tightens emulator runtime behavior without claiming new original-device protocol semantics:

- ECO/power-saving brightness is re-evaluated once per second, so a static framebuffer now changes brightness when the configured interval begins or ends even when no renderer requests a refresh;
- malformed power-saving records (invalid hour/minute/reduction fields) are ignored while the existing compatibility ACK is preserved because an original-device error ACK is still unknown;
- BUILD 99 changes `03/80` into a destructive emulator reset; current BUILD 141 also clears the volatile Preset/Default bank. Carousel, Preset, Alarm, Schedule, brightness, ECO and rotation return to defaults, while the live-reset policy preserves the synchronized software clock and BLE session;
- when RTC support is compiled in, `rtc.lostPower()` now marks the RTC time as invalid. Alarm, Schedule and ECO do not use that RTC value until a valid BLE time synchronization updates it.

The soft-reset and ECO policies above are emulator implementation behavior. Exact original-device behavior remains only partially reverse-engineered.

## Cross-core synchronization hardening

BUILD 86 serializes shared protocol/runtime state between FA02/server BLE callbacks and the Arduino `loop()` with a FreeRTOS task mutex. Earlier builds deliberately deferred AnimatedGIF open/teardown work to `loop()`, but scalar flags, packet/Bulk timeout cleanup, renderer state and connection state could still be read or modified concurrently on the ESP32 BLE task and loop task. BUILD 86 removes the remaining reliance on `volatile` as a synchronization mechanism for those paths.

The mutex is intentionally a scheduler mutex rather than a critical-section spinlock: filesystem, decoder and rendering operations may block and therefore must not execute with interrupts disabled. This does **not** yet move the complete FA02 parser/filesystem pipeline out of the BLE callback; that larger architectural change remains tracked as technical debt.

BUILD 88 fixes one concurrency/timing regression exposed by hardware testing of BUILD 87. After BUILD 86 introduced the runtime mutex, `loop()` still captured its `millis()` snapshot before waiting for that mutex. A BLE callback could therefore update the protected packet/Bulk receive timestamp while the loop was blocked, making the loop snapshot older than the new receive timestamp. The unsigned timeout subtraction then wrapped and could immediately abort an otherwise healthy multi-packet transfer. BUILD 88 takes the time snapshot only after acquiring the mutex. Timeout durations and protocol semantics are unchanged.

BUILD 87 hardens optional infrastructure without changing observed BLE command semantics:

- ArduinoOTA remains disabled by default, and enabling it with the repository Wi-Fi placeholders or the development OTA password now fails at compile time;
- the OTA password must be at least eight characters;
- LittleFS is first mounted non-destructively; the current public repository default sets `LITTLEFS_FORMAT_ON_MOUNT_FAIL=1`, so a failed mount is followed by one format-and-retry recovery attempt;
- set `LITTLEFS_FORMAT_ON_MOUNT_FAIL=0` when preserving an unreadable filesystem for forensic recovery is more important than automatic first-use recovery;
- when LittleFS is unavailable, persistent Preferences metadata is still loaded, but filesystem-backed media operations fail safely instead of pretending storage is available;
- normal Bulk GIF reception checks current LittleFS free space before opening an RX file.

BUILD 89 removes the legacy full-RAM GIF path used by Alarm/Schedule. Their persistent transactional media files are never opened directly by AnimatedGIF: before playback, the selected GIF is copied and CRC-checked into the disposable `/event_play.gif` file. The decoder opens only this isolated PLAY copy, so later staging/backup/rename operations on Alarm/Schedule source files cannot invalidate an active decoder file handle. The event PLAY file is removed when playback stops and is discarded at boot because it is never authoritative persistent state.

The disconnect callback no longer calls `delay(300)`. It records a deferred advertising-restart request, and `loop()` restarts advertising after the same 300 ms interval. This preserves the established reconnect timing while removing an avoidable sleep from the BLE callback.

## Supported hardware targets

### Supported and validated

- **Classic ESP32** — official v0.4.0 reference target and hardware-tested end to end with the 16x16 WS2812B development setup.

### Experimental / unsupported

- **ESP32-C3** — not an officially supported v0.4.0 target. The firmware can boot and execute substantial parts of the runtime when the pin mapping is adapted, but current FastLED channel/driver behavior has produced output timeouts during testing. The classic-ESP32 default pin mapping is also not safe for direct reuse on C3. No compatibility guarantee is provided.
- Other ESP32 variants are not considered supported unless explicitly hardware-tested.

### Planned

- **ESP32-S3** — planned for the next development phase, especially for native 64x64 HUB75 output and PSRAM-enabled testing.

For this project, “supported” means hardware-tested end to end, not merely compilable on a given ESP32 family.

## Display backend and resolution model

BUILD 123 separates the iDotMatrix **logical** resolution from the **physical** display resolution and from the hardware output backend.

```cpp
#define DISPLAY_BACKEND_WS2812  0
#define DISPLAY_BACKEND_HUB75   1
#define DISPLAY_BACKEND DISPLAY_BACKEND_HUB75

#define IDOTMATRIX_SCREEN_TYPE 4   // logical 64x64 profile
#define PHYSICAL_MATRIX_WIDTH  64
#define PHYSICAL_MATRIX_HEIGHT 64
```

The final output stage handles all supported 16/32/64 combinations automatically. Equal dimensions are copied 1:1, upscaling uses nearest-neighbour replication, and downscaling uses box averaging so thin pixel-art/text details contribute to the reduced image. Renderers, BLE protocol handlers, GIF playback and text remain unaware of the physical display type.

The current MatrixPortal S3 reference target is an Adafruit MatrixPortal S3 (ESP32-S3, 8 MB flash, 2 MB PSRAM) driving a 64x64 1/32-scan HUB75 panel through `ESP32-HUB75-MatrixPanel-DMA`, matching the native WLED HUB75 driver family and pinout. The legacy WS2812/FastLED backend remains available at compile time.

For the current MatrixPortal development target use the pinned PlatformIO environment and HUB75 DMA driver documented in `docs/PLATFORMIO.md`. Arduino-ESP32 4.0.0-alpha is not a reference toolchain for this project.

BUILD 125 adds PlatformIO as the recommended iterative development path. The default environment `matrixportal_s3_hub75_64` pins Arduino-ESP32 3.3.11 through pioarduino, selects the MatrixPortal S3 board, uses a project-local 8 MB LittleFS-compatible partition table, and pins the primary external libraries. Arduino IDE remains supported. See [`docs/PLATFORMIO.md`](docs/PLATFORMIO.md).

## Device Assets carousel (v0.4.0-dev / BUILD 97)

The official app exposes three UI pages/lists of twelve positions, but current captures and independent original-hardware reverse engineering indicate one **12-slot device bank**. The app-side pages are alternative sets that are pushed into device slots `0..11`.

The setup frame observed before both short and full page pushes is:

```text
11 00 02 01 0C 00 01 02 03 04 05 06 07 08 09 0A 0B
```

`0x0C` is the number of slot IDs carried by this setup descriptor, not the number of occupied assets. A three-item page still carries all twelve IDs.

Bulk header observations now include:

- bytes 13..14: `timeSign`, little-endian dwell time in seconds;
- byte 15: `imageIndex`, Device Assets slot `0..11`;
- project captures directly confirm `timeSign=5` and `timeSign=30` with indices `0,1,2`;
- a full 12-position push exposed a **TEXT Bulk between GIF indices 4 and 6**. BUILD 95 therefore treats a TEXT Bulk with `imageIndex=0..11` during an open Device Assets push as a persistent carousel slot rather than a live TEXT command. The next hardware log should confirm whether that TEXT carries `imageIndex=5` and the same `timeSign`.

BUILD 95 sequencing was hardware-tested successfully; BUILD 96 added and hardware-validated an output-only upload blackout. BUILD 97 consolidates the same behavior:

1. `0A/01` establishes Device Assets view intent. It may arrive before a later page push and is not assumed to be repeated afterwards.
2. `02/01` starts replacement of the declared device slots. Current carousel playback is stopped. BUILD 96/97 forces the physical matrix black for the replacement window while keeping the logical framebuffer and app-controlled `screenOn` state intact.
3. During the replacement, GIF and observed TEXT Bulk transfers with `imageIndex=0..11` are stored directly in their corresponding slots. They are **not rendered live while the push is still in progress**.
4. `timeSign` is persisted per slot as the carousel dwell.
5. No explicit end-of-push command has yet been observed after short page uploads. If Assets view was already requested, the emulator waits for a conservative **3-second interval with no active Bulk and no newly committed carousel asset**, then closes the replacement and releases the upload blackout. If Assets view is active, the first populated slot starts; otherwise the preserved framebuffer is restored. This settle interval and blackout are emulator policies, not claimed original-device protocol behavior.
6. Each populated slot advances after its dwell. GIF slots loop through AnimatedGIF; TEXT slots use the existing text renderer for the same dwell. Empty slots are skipped.
7. A normal live/Cloud GIF or TEXT outside an open Device Assets replacement keeps the stable v0.3.1 behavior.
8. Hardware testing confirms that an already-running carousel continues after the official app disconnects.

Independent hardware-validated reverse engineering also documents a 12-slot autonomous carousel, `timeSign`, `imageIndex`, material setup/wipe and `0A/01`. That external work currently describes persistent slots as GIF-based; the mixed TEXT slot seen in our current official-app capture is therefore tracked as a local protocol extension that still needs direct validation.

## 64x64 findings

The official app accepts screen type `0x04` and serves 64x64-specific cloud animations. Tests successfully received and played GIFs approaching 80 KB on the classic ESP32. The important architectural change was not more RAM: large GIFs are streamed to LittleFS, RX and PLAY files are isolated, and the AnimatedGIF decoder is destroyed/recreated for each media change. This removed the heap corruption and BLE disconnects seen during early 64x64 experiments.

## Buzzer

The tested Arduino-kit buzzer is an **active buzzer**. GPIO18 is therefore driven digitally rather than with `tone()`. Alarm audio uses a non-blocking repeating three-pulse trill so BLE, LEDs and OLED continue running. Program/Schedule uses one three-pulse trill at activity start, and Countdown uses the same one-shot triple pulse when it reaches zero naturally. BLE connection feedback is a separate single 90 ms pulse. It is intentionally low priority and is skipped if Alarm or another buzzer notification is already active.

## Security considerations

The default firmware is an experimental BLE peripheral emulator and does not currently require BLE pairing/authentication before accepting iDotMatrix commands. A nearby BLE central able to connect to the advertised device can therefore control the display and send supported configuration/media commands. This behavior is kept for compatibility with the official app and should not be interpreted as an authenticated control channel.

Wi-Fi/ArduinoOTA support is compile-time optional and disabled by default. BUILD 87 adds compile-time guards: a build with `OTA_ENABLED=1` fails if the repository Wi-Fi placeholders are still present, if the development OTA password `idotmatrix-ota` is still present, if any credential string is empty, or if the OTA password is shorter than eight characters. These checks prevent accidental deployment of the repository defaults; they do not turn OTA into a substitute for network isolation or BLE authentication.

## LittleFS safety and recovery

The emulator always attempts a non-destructive LittleFS mount first. The current public repository default is `LITTLEFS_FORMAT_ON_MOUNT_FAIL=1`, so first-use or incompatible/corrupted filesystem cases get one format-and-retry recovery attempt. Set the option to `0` if preserving an unreadable filesystem is more important than automatic recovery.

### MatrixPortal S3 / Arduino IDE partition requirement

The current emulator storage backend requires an Arduino partition scheme containing a **SPIFFS/LittleFS-compatible data partition**. The MatrixPortal S3 may default to a FAT-oriented partition scheme in Arduino IDE; that configuration leaves LittleFS unavailable even when format-on-mount-failure is enabled. Select a partition scheme with SPIFFS/LittleFS-compatible storage before testing GIF, Carousel, Alarm or Schedule media. FAT-only schemes are not supported by the current storage backend.

When LittleFS is offline, the emulator can still load Preferences metadata and continue with non-filesystem features, but filesystem-backed GIF, Alarm media and Schedule media cannot be stored or played until storage is available.

## Intentional differences from original hardware

Protocol compatibility does not require reproducing every original-device UX decision. The following differences are deliberate and should not be reported as compatibility defects.

| Original 64×64 behavior | Emulator behavior | Rationale |
|---|---|---|
| Boot logo/fade can be shown | No cosmetic boot animation | Faster, cleaner startup |
| BLE connection shows a visual animation/logo | Existing display content is preserved; one short 90 ms beep is used instead | Non-intrusive connection feedback |
| Leaving Cloud GIF returns to background content | Cloud GIF remains visible/running | Better standalone behavior |
| Leaving Graffiti returns to background content | Graffiti remains displayed | Better standalone behavior |
| Countdown completion is silent | One three-beep notification | Useful completion feedback |
| Program/Schedule buzzer repeats for roughly 30 s | One three-beep notification | Less intrusive |
| Snowflake text is constructed by falling strokes/lines | Custom snow visual effect | Preferred visual interpretation |
| Laser text is constructed from a right-arriving beam | Custom scan-line laser effect | Preferred visual interpretation |
| No persistent RTC; time is lost on power cycle | Optional RTC support is planned/supported at compile time | Enables autonomous clock and scheduling |
| Stored Device Assets resume after boot | Boot policy is valid RTC → Clock, else valid Carousel → Carousel, else screen off | Deterministic standalone behavior |

See [`docs/ORIGINAL-HARDWARE-64X64.md`](docs/ORIGINAL-HARDWARE-64X64.md) for the hardware-oracle record and pending physical inspection notes.

## Development update helper

`update_idotmatrix_emulator.sh` is shipped in the repository root. It updates the Git working tree from the newest source ZIP, preserves `.git/` and `.pio/`, checks the MatrixPortal serial device, compiles without uploading, verifies the generated firmware signature, performs a second mandatory serial check, and only then offers the upload step. The second check is intentional for MatrixPortal S3 + WSL/usbip setups where the board can switch USB endpoint/mode and must be re-bound/re-attached before flashing. Every operational stage asks for confirmation and the script never uploads firmware automatically.
