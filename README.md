# iDotMatrix ESP32 Emulator

Experimental ESP32 firmware that emulates the **iDotMatrix BLE peripheral** and communicates directly with the official iDotMatrix app. The stable hardware target is currently 16x16, with experimentally verified 32x32 app-profile support.

       alt="iDotMatrix ESP32 Emulator running on a 16x16 LED matrix"

</p>

This project was created by reverse engineering the BLE traffic generated by the app, without access to an original iDotMatrix device. The goal is to reproduce as many app features as possible on ESP32-driven LED matrices while documenting the observed device-side protocol. Development started on a 16x16 WS2812B matrix and the firmware now contains a multi-size framework used successfully to simulate the 32x32 application profile.

> Current status: **BUILD 67**, current consolidated baseline. Verified on the physical 16x16 development matrix; the 32x32 app profile has also been successfully simulated and exercised.

## Hardware used

Current development setup:

- DollaTek ESP32 OLED 0.96" board with ESP32 and CP2102;
- 16x16 WS2812B matrix, 256 LEDs;
- matrix GPIO: **17**;
- status LED: **GPIO 25**;
- onboard 128x64 SSD1306 OLED:
  - SCL: GPIO 15
  - SDA: GPIO 4
  - RESET: GPIO 16
  - driven through U8g2 software I2C;
- active buzzer on **GPIO 18**, verified on hardware and used by Alarm/Schedule with a non-blocking trill pattern;
- DS3231 RTC: optional support is implemented but not installed.

Maximum FastLED brightness is limited by `MAX_LED_BRIGHTNESS` (currently 50/255) to keep matrix current consumption under control.

## Implemented features

The firmware currently supports:

- BLE advertising recognized by the app;
- observed FA/AE services and characteristics;
- configurable iDotMatrix device profile, including verified 16x16 (`0x01`) and simulated 32x32 (`0x03`) identification;
- date/time synchronization from the app;
- matrix power on/off;
- 180-degree rotation;
- brightness with NVS persistence;
- scheduled power saving;
- solid color;
- drawing/graffiti mode;
- resolution-aware RAW RGB images;
- animated GIFs;
- text with glyphs, colors, background and effects, including 8x16 (`0x02`) and 16x32 (`0x05`) glyph records;
- visual effects;
- clock and multiple clock styles;
- scoreboard;
- 10 audio visualizations: 5 LEVEL and 5 FFT;
- persistent alarms with associated media;
- persistent Programs/Schedules with GIF, text and PNG activities;
- resolution-aware PNG handling for Schedule content;
- optional diagnostic OLED;
- prominent OLED notification for unknown BLE commands.

Countdown and stopwatch are implemented locally, but app-side compatibility is not yet complete. See [TODO.md](TODO.md).

## Arduino dependencies

The source uses:

- ESP32 Arduino Core;
- FastLED;
- AnimatedGIF;
- U8g2 when `OLED_STATUS_ENABLED` is enabled;
- LittleFS and Preferences from the ESP32 core;
- RTClib only when `RTC_ENABLED` is set to 1.

The PNG decoder uses `miniz` from the ESP32 core/SDK and does not require an external PNG library.

## Flash partitioning

During development the firmware outgrew the application space available with the OTA partition layout. Since OTA is not used, the board is compiled with a partition layout providing about **2 MB for the application without OTA**.

If the firmware grows further, a layout with about 3 MB for the sketch can be used while still leaving enough room for LittleFS.

## Main configuration

The most important settings are grouped near the beginning of `src/IDotMatrix.ino`, including:

```cpp
#define FW_BUILD               67
#define DEBUG_SERIAL           1
#define OTA_ENABLED            0
#define MATRIX_PIN             17
#define STATUS_LED_PIN         25
#define MAX_LED_BRIGHTNESS     50
#define IDOTMATRIX_SCREEN_TYPE  1   // 1=16x16, 3=32x32 experimental profile
#define PHYSICAL_MATRIX_WIDTH   16
#define PHYSICAL_MATRIX_HEIGHT  16
#define OLED_STATUS_ENABLED    1
#define RTC_ENABLED            0
#define ALARM_BUZZER_ENABLED   1
#define ALARM_BUZZER_PIN       18
#define ALARM_SLOTS            10
#define SCHEDULE_MAX_ACTIVITIES 32
```

### Diagnostic OLED

The onboard OLED can be completely removed at compile time with:

```cpp
#define OLED_STATUS_ENABLED 0
```

BUILD 67 retains the **pure event-driven OLED mode** introduced in B62. Because this board uses U8g2 software I2C, continuously transferring the full SSD1306 framebuffer caused visible stalls in the WS2812B animations in BUILD 60/61. B62 sends a new OLED framebuffer only when meaningful state changes occur.

The OLED reports build number, BLE connection, matrix power, current mode, brightness, Schedule/Alarm state, timer state and unknown commands. Unknown commands display their length and the first raw bytes, which is useful when the serial monitor cannot be used while the matrix is connected.

## Persistent storage

Two mechanisms are used:

- **Preferences / NVS** for small settings and metadata;
- **LittleFS** for alarm and Schedule media.

Brightness is also persisted so that reconnecting the app does not temporarily restore an incorrect default intensity.

## Reverse-engineering notice

This is an independent interoperability/research project based on observing the behavior of the iDotMatrix app and the BLE packets it transmits. No original iDotMatrix firmware was copied or extracted, and the project was developed without an original hardware device.

The protocol documentation describes experimentally observed behavior. Some fields are still unknown or only partially understood; these are explicitly marked as such.

## Related projects and prior work

Most existing open-source iDotMatrix projects implement the **client/controller side** of the protocol: they connect to original iDotMatrix hardware and send commands to it. This project approaches the protocol from the opposite direction: the ESP32 emulates the BLE peripheral itself, allowing the official mobile application to connect directly to the emulator.

As far as we are aware, this is the first public ESP32 implementation that emulates an iDotMatrix BLE peripheral. If you know of an earlier device-side implementation, please let us know.

Useful related projects include:

- `derkalle4/python3-idotmatrix-client` — Python controller and early reverse-engineering work for 16x16/32x32 displays.
- `8none1/idotmatrix` — protocol reverse engineering, including transfer framing and ACK behavior.
- `dallanwagz/idotmatrix-ha` — Home Assistant integration tested against original 32x32 hardware.
- `markusressel/idotmatrix-api-client` — modern Python API client for iDotMatrix displays.

Our protocol findings were independently derived from the official app and ESP32 emulator, and are now being cross-checked against these implementations and hardware-derived captures. See [`docs/PROTOCOL-COMPARISON.md`](docs/PROTOCOL-COMPARISON.md).

## Multi-size testing wanted

Build 67 keeps **16x16 as the default physical/logical target**, but the firmware now has a multi-size framework. The ESP32 has been successfully advertised as a **32x32 iDotMatrix profile (`0x03`)**: the official app switched to higher-resolution cloud assets, exposed 16/32 text-size options, and Graffiti operated with 32x32 coordinates.

The physical 32x32 matrix has not yet been tested. We are looking for testers with **32x32 or 64x64 WS2812B-compatible matrices**, especially anyone who also owns an original iDotMatrix of the same size.
